## 二、耦合度分析

### 2.1 依赖关系图

```
hd2_guard（独立）
   │
hd2_monitor（被 5 个插件埋点调用）◄────┐
   │                                  │
   ├── hd2_lookup                     │
   ├── hd2_roll                       │
   ├── hd2_planet_info ──┐            │
   ├── hd2_variant_query ─┼──► 共享表: effect_id_cn.json
   └── hd2_war_report ────┘          │
          │                          │
          ├──► tables/ (对照表/星图表/dss_effects/effect_id_cn)
          ├──► cache/ (mo_cache / dss_news_cache / news_cache)
          ├──► LLM (AstrBot provider: deepseek)
          └──► 3 个数据源 (官方 API / companion / helldivers2.dev)
```

### 2.2 耦合度分级

| 耦合类型 | 涉及 | 严重度 | 说明 |
|---|---|---|---|
| **共享表依赖** | planet_info / variant_query / war_report 共用 `effect_id_cn.json`、对照表 | 🟡 中 | 表结构约定靠"默契"，无 schema/版本管理；新增效果需同步改 3 处读取逻辑 |
| **监控埋点依赖** | 5 个插件 `from astrbot_plugin_hd2_monitor.main import hd2_log` | 🟢 低 | 有 try/except 兜底（monitor 缺失时退化为 no-op），符合 AstrBot 插件间协作惯例 |
| **数据源重复实现** | 3 个插件各自实现 `_fetch_official` / `_fetch_json` / `OFFICIAL_API_URL` / `_load_effect_id_cn` | 🟡 中 | 同函数在 3 处重复定义（约 4 组 × 3 份），改一处易漏另外两处 |
| **星球译名重复** | `PLANET_NAME_CN` 在 2 个插件重复定义（planet_info / war_report） | 🟡 中 | 新增星球需同步 2 处；实际已出现过漏改（UVP 星系 Unknown bug） |
| **缓存目录** | war_report 独有 cache/（mo/dss/news） | 🟢 低 | 单插件内部，无跨插件竞争 |
| **环境变量** | 推送脚本依赖 `HD2_PROJECT_DIR`，表文件读取依赖它做兜底 | 🟢 低 | 已设置 User 环境变量 + 表文件复制插件目录双兜底 |
| **LLM 依赖** | war_report 翻译（MO 简报/新闻/DSS）依赖 AstrBot provider 配置 | 🟢 低 | 失败有本地翻译/原文兜底，不阻断 |

### 2.3 耦合风险点

1. **war_report 单体过大（1817 行）**：一个文件承载 MO 抓取+翻译、新闻、DSS、战线、战役、战局分析、跃迁封锁、缓存、多数据源回退——功能密度最高，修改牵一发而动全身。
2. **planet_info 与 variant_query 高度同源**：都做"星球行动变量扫描"，代码模式相似但各自实现，存在重复。
3. **三插件重复的数据源层**：官方 API 头部（X-Super-Client）、超时/重试、companion 兜底逻辑，3 份拷贝。
4. **对照表是"用户维护的 Markdown"**：机器人解析 Markdown 提取 `[ID]` 标注，格式约定脆弱——用户改格式即可能解析失效。

## 三、可维护性评估

| 维度 | 评分（1-5） | 依据 |
|---|---|---|
| 模块职责划分 | ⭐⭐⭐⭐ 4 | 7 个插件职责清晰、命名统一（hd2_*），单插件内功能内聚 |
| 代码可读性 | ⭐⭐⭐ 3 | 中文注释充分、函数命名语义化；但 war_report 超长、魔法数字多（valueTypes=3/12） |
| 复用性 | ⭐⭐ 2 | 数据源层/星球译名/效果表读取在插件间复制粘贴，无公共库 |
| 配置管理 | ⭐⭐⭐ 3 | config.json + 环境变量 + 表文件三处配置来源，需文档说明 |
| 部署一致性 | ⭐⭐⭐ 3 | 需手动同步 4 个副本（HD2-Bot/hd2-bot/Release/部署版），无自动化脚本 |
| 错误处理 | ⭐⭐⭐⭐ 4 | 官方/社区双源回退、缓存兜底、monitor 埋点 no-op 兜底，容错意识强 |
| 可测试性 | ⭐⭐ 2 | 无单元测试框架；验证靠手工跑脚本 + 群测 |
| 文档 | ⭐⭐⭐ 4 | README/使用说明/部署指南/抓取指南/工作报告齐全；缺架构图与表格式规范 |

**维护难点排行**：
1. 4 副本手动同步（改一行 = 同步 3 处，CRLF 差异坑）
2. 数据源层三份拷贝（官方 API 结构变更要改 3 个文件）
3. 对照表格式约定无校验（录入脚本依赖 `[ID]` 标注）
4. 官方 API 不稳定（时好时坏 500），回退链路测试成本高

## 四、开源隐患综合评判

### 4.1 合规/许可

| 隐患 | 等级 | 说明 |
|---|---|---|
| **官方 API 抓包使用** | 🔴 高 | 通过抓包逆向 `api.live.prod.thehelldiversgame.com`（X-Super-Client 头）获取数据。属非官方公开 API，违反服务条款风险存在；`X-Super-Client` 头为规避风控手段 |
| **companion 数据复用** | 🟡 中 | 依赖 helldiverscompanion.com 聚合接口（社区项目），若其上游被官方封禁则全链路受影响；companion 本身 AGPL 许可，**仅调用其公开接口不复制源码**则风险可控 |
| **helldivers2.dev 使用** | 🟢 低 | 该站提供公开 API（含 zh-Hans），是社区合法数据源 |
| **LLM 翻译** | 🟢 低 | 走 AstrBot 自带 provider（deepseek），无额外许可问题 |
| **AI 生成代码版权** | 🟡 中 | 大量代码由 AI 生成，若开源需注明；LICENSE 已存在（需确认类型） |

### 4.2 安全/敏感信息

| 隐患 | 等级 | 说明 |
|---|---|---|
| **API key 泄漏风险** | 🟢 低（已排查） | **已实测确认**：Release `data/cmd_config.json` 的 provider 为空数组、无任何 sk- key；真实 key 仅存在于部署版本地 `C:\Users\37420\.astrbot\data\cmd_config.json`。开源安全 |
| **群白名单硬编码** | 🟢 低 | QQ 群号/用户 ID 属敏感信息，开源前应抽离为配置 |
| **NapCat token** | 🟡 中 | 6099 端口 token 若入仓库，外部可调用推送接口（当前在本地配置，需确认不入库） |
| **监控日志** | 🟡 中 | `指令日志.jsonl` 含群消息内容，开源前需清洗 |

### 4.3 工程/运营

| 隐患 | 等级 | 说明 |
|---|---|---|
| **官方 API 稳定性依赖** | 🔴 高 | 官方 Status API 时好时坏（曾全天 500），开源后用户会遇到"时灵时不灵"体验 |
| **游戏版本耦合** | 🟡 中 | 新内容（新星球/新变种/新效果）需人工跟进对照表，不跟进即显示英文/Unknown |
| **多副本漂移** | 🟡 中 | 4 副本手动同步，开源后用户拿到的是 Release 快照，后续修复未必回传 |
| **4 处数据源头部硬编码** | 🟢 低 | 无密钥，仅 UA 标识 |

## 五、功能建议（按优先级）

### P0（开源前必做）
1. **敏感信息脱敏**：确认 Release `data/cmd_config.json` 不含真实 key；NapCat token、群号、用户 ID 全部抽到 `.env.example` / `config.example.json`
2. **新增公共基础库**：抽 `hd2_common`（或 `hd2_lib`）——统一 `_fetch_official/_fetch_json/PLANET_NAME_CN/_load_effect_id_cn/_load_starmap_sectors`，三插件改为 import，消除重复拷贝
3. **一键同步脚本**：`sync_plugins.py` 将开发版 → Release/部署版自动复制 + CRLF 规范化 + 编译校验，杜绝手工漏同步

### P1（体验提升）
4. **官方 API 健康监测**：war_report 启动时探活官方端点，失败自动切换 companion 并记录；对用户透明
5. **war_report 拆分**：把 1817 行拆为 `mo.py`（MO+进度）/ `dss.py` / `news.py` / `warzone.py` / `warp.py`，单文件职责回归 <600 行
6. **对照表 schema 化**：把用户维护的 Markdown 保留为"人读"源，另加机器可读 `variables.json`（由录入脚本生成），解析不再依赖 Markdown 格式

### P2（功能增强）
7. **新内容自动提醒**：每日定时抓 companion，检测新星球/新效果/新 NMO，自动生成"待录入清单"推送给维护者（替代人工盯新闻）
8. **LLM 翻译缓存持久化**：news_cache 已做，扩展 MO 简报缓存（已做 mo_cache）；可再加"翻译失败重试队列"
9. **多语言/国际化**：术语表已支持中英，可扩展繁体/日文
10. **WebUI 增强**：8630 控制台加"表文件在线编辑 + 一键同步部署"（维护者友好）

### P3（远期）
11. **数据源抽象层**：定义 `DataSource` 接口（官方/companion/hd2dev 三实现 + 失败降级策略），为"汉化星图站方案 B"复用
12. **开源协作规范**：CONTRIBUTING.md + issue 模板 + GitHub Actions 自动构建校验

## 六、结论

**整体评价**：架构方向正确（插件化、多数据源容错、用户维护对照表），作为一个"个人→群"的实战机器人，可靠性设计（双源回退/缓存兜底/埋点监控）明显超出同类插件平均水平。

**最大短板**：① 共享代码复制粘贴导致维护成本随功能线性增长；② war_report 单文件过载；③ 开源前安全审计未完成（key/token/白名单）。**【已实测】key 泄漏风险已排除**（Release 配置已脱敏），NapCat token 与群白名单仍需开源前抽离。

**建议路线**：先做 P0 三项（脱敏 + 抽公共库 + 同步脚本），再拆 war_report，其余按需推进。完成 P0 后，该项目具备开源条件，且"官方 API + 社区兜底 + 用户对照表"的数据架构本身就有差异化价值。
